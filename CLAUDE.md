# applyd-bootcamp

- For ALL UI/styling work, follow the color scheme and rules in `DESIGN.md` (red `#c73a41` + charcoal `#272827`). Do not introduce colors outside that palette.
- The served stylesheet is `public/css/app.css` (not `resources/css/app.css`).

## Stack conventions

- **Data tables:** ALWAYS use `rappasoft/laravel-livewire-tables` (docs: https://rappasoft.com/docs/laravel-livewire-tables/v4/introduction) for any admin/data table — never hand-rolled Blade tables. Components live in `app/Livewire/*Table.php` (see `RegistrationsTable`, `SchedulesTable`). Installed version is v3.8 (v4 has no stable release yet; upgrade when it ships). Livewire 3 is installed.
- **Admin UI:** `layouts/admin.blade.php` — charcoal sidebar layout (logo, nav items, user card, logout). Tailwind Play CDN is loaded on admin pages only (for the Livewire table theme); public pages use `public/css/app.css` alone.
- **Roles & permissions:** `spatie/laravel-permission`. Roles (student/lecturer/admin/super seeded) and permissions are DB-driven, managed at `/dashboard/roles` (permission `manage roles`, super-only by default); users at `/dashboard/users` (`manage users`). Middleware aliases are spatie's: `role:admin|super` (pipe-separated) and `permission:manage users`. The `super` role always keeps all permissions and can't be renamed/deleted; the legacy `users.role` column is gone — use `$user->hasRole()` / `$user->role_label`. Gate UI with `@can` / `@canany`.
- **Select2 everywhere:** all plain `<select>` inputs get Select2 with search (global init in both layouts). Livewire-controlled selects (inside `[wire:id]`) and anything with `data-no-select2` are excluded — don't Select2-ify those.
- **Dashboard home:** `/dashboard` is an overview page (stat cards + link cards to each section); the registrations table lives at `/dashboard/registrations`.
- **Public pages** extend `layouts/app.blade.php` (sticky white navbar + rich charcoal footer). Landing schedule table is DB-driven (`schedules` table, managed at `/dashboard/schedules`). Tools are DB-driven too (`tools` table, managed at `/dashboard/tools`) — the landing card grid, filter tabs, registration form picker, and validation all read from it; `config('bootcamp.tool_categories')` is only the migration seed.
- **Confirmations:** admin uses SweetAlert2 (CDN in `layouts/admin.blade.php`) — add `data-confirm="message"` to any form instead of `onsubmit confirm()`.
- **Exports:** every admin table gets its own "Export Excel" button (`.page-head` next to the title) backed by `maatwebsite/excel` and an export class in `app/Exports/`. No export links in the sidebar.
- **Admin sidebar:** grouped sections via `.side-heading` (Bootcamp / Academy / General), plain text nav items — no emoji/icons. Courses CRUD lives under Academy (`/dashboard/courses`).
- **Phone country codes** come from `giggsey/libphonenumber-for-php` via `App\Support\PhoneCountries` — don't hardcode country lists.
- **Transactional email:** delivered over the client's **cPanel SMTP** (`MAIL_MAILER=smtp`, `mail.<domain>`, port 465/`smtps`, username = full address — see `.env.example`). Every customisable email is declared in `config/email_templates.php` (default copy + placeholder list); admins override subject/heading/body/CTA at `/dashboard/email-templates`, stored in `email_templates` and merged by `EmailTemplate::resolve()`. Send through `App\Services\EmailNotificationService` (never `Mail::` directly for participant mail) — it renders `{{ token }}` placeholders, writes an `email_logs` row, and swallows/records failures so a mail outage can't break a request. `App\Mail\TemplatedMail` + `resources/views/emails/template.blade.php` are the shared wrapper. Bootcamp registration fires `sendRegistrationConfirmation()` alongside the SMS. Resends: per-row + bulk on the registrations table, the registration detail page, and `/dashboard/email-logs` (mirrors the SMS Delivery screen). The cPanel host must be the server hostname the TLS cert covers (`premium349-2.web-hosting.com`), **not** `mail.<domain>` — the shared-hosting cert is `*.web-hosting.com` and `mail.applydacademy.com` fails the handshake.
- **Bulk compose:** tick rows on `/dashboard/registrations` → bulk action "Send email to selected…" stashes the ids in the session (`BulkEmailController::SESSION_KEY`) and redirects to a compose screen (`Dashboard\BulkEmailController`). The message is rendered **once per recipient** so `{{ first_name }}` resolves individually, logged to `email_logs` with `template_key = bulk_broadcast`. Sends are synchronous — large selections block the request. **Registrants with `marketing_opt_in = false` are excluded by default and the exclusion is enforced server-side**, not just in the UI — the compose screen lists them in a separate "Excluded — opted out" panel and they get no `email_logs` row at all. The single override is a `service_message` checkbox, for mail consent doesn't govern (schedule change, joining link, cancellation); the skipped count is always reported back in the flash message so a drop never looks like a delivery failure. Transactional confirmation resends are unaffected — marketing consent doesn't gate them.
- **Filtering registrations by tool:** `RegistrationsTable::filters()` exposes a `MultiSelectFilter` whose options come from the `tools` table (never a hardcoded list). `registrations.tools` is a JSON array, so the callback OR-s `whereJsonContains()` per selected value — "anyone who picked any of these". That compiles to `json_contains()` on MySQL and `json_each()` equality on SQLite: exact element matching on both, never a substring. Note rappasoft validates multi-select values against the options list and silently discards unknown ones, so a tool deleted from `tools` stops being filterable (and tests must create the tools they filter on rather than leaning on the migration's seed list).
- **Deleting registrations:** per-row `Delete` button + `Delete selected` bulk action on `RegistrationsTable`, both gated on the existing `manage registrations` permission (checked server-side in `performDelete`/`performDeleteSelected` — Livewire methods are publicly callable, so the `@can` in the Blade partial is presentation only). Deletes are **permanent** — `Registration` has no `SoftDeletes`. Delivery history is preserved: `sms_logs.registration_id` is `ON DELETE CASCADE` at the DB level, so `detachLogs()` nulls it first to match `email_logs`' `nullOnDelete` — the person goes, the record of what we sent them stays. Confirmation uses the SweetAlert2 `confirm()` helper on the component (there is no form to hang `data-confirm` on in a Livewire action); `deleteRow`/`deleteSelected` only raise the dialog, the `perform*` methods do the work.
- **Rich text + images:** `resources/views/partials/quill.blade.php` is the shared Quill editor (`<textarea data-rich>`). Its image button uploads to `POST /editor/image` (`Dashboard\EditorImageController`, `auth` middleware, public disk under `editor/`) and embeds an **absolute** URL — never Quill's default base64, which mail clients strip. The button is hidden for guests. `App\Support\Html::clean()` allow-lists `img[src|alt|width|height]` and restricts URI schemes to http/https/mailto, so `data:` and `javascript:` sources are dropped. HTMLPurifier runs an HTML 4.01 doctype — HTML5 tags (`figure`, `figcaption`) throw, so don't add them to the allow-list.
- **Job board:** companies sign up at `/companies/register` (creates a user with the `company` role + a `Company` profile); company portal at `/company` (`layouts/company.blade.php`, role:company) for posting jobs and reviewing applications. Public board at `/jobs` (`JobOpening::open()` scope); applicants apply without an account, uploading CV + up to 5 supporting docs. **Application files are stored on the private `local` disk** (`storage/app/private/applications/...`), never the public disk — downloads only via authorized `company.applications.cv`/`.document` routes (owner-checked). Login redirects by role: company → `company.home`, others → `dashboard`.
- **Session videos:** recordings of past sessions, hosted on YouTube — the site never stores video files. CRUD at `/dashboard/videos` (`SessionVideoController` + `SessionVideosTable`, drag to reorder, Export Excel), public at `/videos` (`PageController::videos`, paginated) plus the newest three on the landing page (`#videos` section, hidden entirely when none are published). Admins paste **any** YouTube link — watch, `youtu.be`, embed, shorts, live — and `SessionVideo::parseYoutubeId()` normalises it to the 11-char id, which is what `session_videos.youtube_id` stores (unique, so the same video can't be added twice). The pasted `youtube_url` is a form field, not a column: parsing happens inside a closure rule so a bad or duplicate link is reported on the field the admin actually filled in. Thumbnails default to YouTube's own still (`i.ytimg.com/vi/{id}/hqdefault.jpg`); a custom upload (public disk, `videos/`) overrides it — the admin table needs `setAdditionalSelects(['session_videos.thumbnail'])` for that to render. Cards in `partials/video-grid.blade.php` are a **facade**: a plain link to the watch URL that script swaps for a `youtube-nocookie` iframe on click, so no YouTube request fires until someone presses play and the card still works without JS. `is_published` gates public visibility (`scopePublished`); ordering is `sort_order` on both sides. All the wording on `/videos` (hero, empty state, bottom CTA) and the landing strip's heading/lead/link is **CMS-editable** — registered under the `videos` page and the landing "Session videos strip" section in `config/cms.php`, read with `cms()`/`cms_html()`. Don't hardcode copy into either view.
- **Talent pool + recruiter credits:** candidates drop a CV at `/talent-pool` (public, no account) tagging up to 5 sectors from `JobOpening::SECTORS`; the file goes to the **private** `local` disk under `talent-pool/cv/`. A company sees a candidate only once it has published a job in a matching sector (`Company::matchingTalent()`), and the name is masked (`masked_name` → "Kwame A.") with **no contact details rendered at all** until it spends a credit — masked server-side, not blurred in CSS. Sector matching OR-s `whereJsonContains()` per sector (exact element match on MySQL and SQLite, never a substring), same shape as the registrations tool filter. **Credits are the only currency**: `creditsBought()` (sum of `plan_purchases` with `status = paid`) minus `creditsUsed()` (rows in `cv_unlocks`) — there is no balance column to drift, and no second way to earn credits. One credit opens one candidate permanently; the unique index on `(company_id, talent_profile_id)` makes a second click free, and the balance is re-checked inside `Company::unlockCv()`'s transaction. Credits never expire and buying again just adds another paid row — that is the whole "expand your plan" story, so there is no renewal, expiry or cron anywhere. **Applications to a company's own job posts stay free and never touch credits.** Plans are admin-CRUD at `/dashboard/recruiter-plans` (purchases snapshot `plan_name`/`credits`, so retiring a plan can't disturb what was bought); recruiters buy at `/company/plans` through the existing Paystack redirect, and `company.plans.callback` sits **outside** the auth group deliberately — verifying a payment must not depend on a live session. Offline payers get credits via the "Add credits by hand" form on `/dashboard/plan-purchases`, which writes a normal settled purchase row rather than inventing a second mechanism.
- **Pulse Check (session surveys):** short check-ins participants fill in around a session — public at `/check-in` (picker) and `/check-in/{slug}`, no login. **Surveys are rows, not config**: admins create as many as they like at `/dashboard/surveys/manage` (`SurveyManagerController` + `SurveysTable`), each with its own slug/URL, QR, questions and results. `config/surveys.php` is **only the migration seed** for both `surveys` and `survey_questions` — nothing in it is read at runtime. `surveys.slug` is the public route key (`Survey::getRouteKeyName()`), auto-generated from the name when left blank and refused for `Survey::RESERVED_SLUGS` (`thanks` would shadow `/check-in/thanks`). `is_active` closes a survey: off the picker, 404 on the form, **results still on the dashboard**. Data outlives the form — `SurveyManagerController::destroy` refuses while any response exists (archive instead), and deletes the survey's questions itself. Both `survey_id` FKs (`restrictOnDelete` on responses, `cascadeOnDelete` on questions) were added by a later `ALTER TABLE`, which **SQLite silently ignores** — so they hold on MySQL only and app-level enforcement is what the tests exercise. Never move that guard back into the database. **Duplicate** copies a survey plus its questions (never its responses) and lands closed — the way to re-run the same check-in for the next session while the previous one keeps its results. Three question types: `choice`, `scale` (answer is the 1-based index, `options` holds the labels), `text`. Answers land in `survey_responses.answers` as a JSON map keyed by the question `key` — which is why the key is set once at creation and **not editable afterwards** (changing it would orphan every answer already collected); deleting or hiding a question likewise leaves its answers in the table. Validation rules are built from the DB rows (`SurveyQuestion::rules()`), so the public form can never accept an option that isn't live. Skipped optional questions are omitted from the map rather than stored as `''`, so "answered" counts stay honest. The public form is a one-question-at-a-time stepper that **degrades to a single long form without JS** (`.pulse-form.is-stepped` is added by script). Results at `/dashboard/surveys`: a tab per survey (`?survey=<slug>`, falling back to the first), aggregates from `App\Support\Surveys::summarise()` counting in PHP (JSON map, bootcamp volumes), with a `SurveyResponsesTable` (`:survey-id`) underneath. The screen is deliberately **minimal until asked**: three stat numbers, then every block (share/QR panel, each question, the raw table) is a native `<details>` that starts closed — so it works without JS — and each question's summary row carries its headline figure (`summarise()` returns `top`, the winning bucket) so the closed state still says something. Cards there are **flat**: `.sv-flat` drops the 1px border and the hover lift, leaving spacing and a soft shadow. Don't put outlines back on them. That table's answer columns are rappasoft **label** columns, and rappasoft only SELECTs fields behind real columns — hence `setAdditionalSelects(['survey_responses.answers'])` in `configure()`, without which every cell silently renders as "not answered". Sharing: QR code on the results page plus a printable poster at `/dashboard/surveys/poster`, both drawn client-side from the route URL via the `qrious` CDN script (no composer dependency, so the QR follows `APP_URL` — check it's right in production).
