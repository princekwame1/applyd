# applyd-bootcamp

- For ALL UI/styling work, follow the color scheme and rules in `DESIGN.md` (red `#c73a41` + charcoal `#272827`). Do not introduce colors outside that palette.
- The served stylesheet is `public/css/app.css` (not `resources/css/app.css`).

## Stack conventions

- **Data tables:** ALWAYS use `rappasoft/laravel-livewire-tables` (docs: https://rappasoft.com/docs/laravel-livewire-tables/v4/introduction) for any admin/data table — never hand-rolled Blade tables. Components live in `app/Livewire/*Table.php` (see `RegistrationsTable`, `SchedulesTable`). Installed version is v3.8 (v4 has no stable release yet; upgrade when it ships). Livewire 3 is installed.
- **Admin UI:** `layouts/admin.blade.php` — charcoal sidebar layout (logo, nav items, user card, logout). Tailwind Play CDN is loaded on admin pages only (for the Livewire table theme); public pages use `public/css/app.css` alone.
- **Roles & permissions:** `spatie/laravel-permission`. Roles (student/lecturer/admin/super seeded) and permissions are DB-driven, managed at `/dashboard/roles` (permission `manage roles`, super-only by default); users at `/dashboard/users` (`manage users`). Middleware aliases are spatie's: `role:admin|super` (pipe-separated) and `permission:manage users`. The `super` role always keeps all permissions and can't be renamed/deleted; the legacy `users.role` column is gone — use `$user->hasRole()` / `$user->role_label`. Gate UI with `@can` / `@canany`.
- **Select2 everywhere:** all plain `<select>` inputs get Select2 with search (global init in both layouts). Livewire-controlled selects (inside `[wire:id]`) and anything with `data-no-select2` are excluded — don't Select2-ify those.
- **Dashboard home:** `/dashboard` is an overview page (stat cards + link cards to each section); the registrations table lives at `/dashboard/registrations`.
- **Public pages** extend `layouts/app.blade.php` (sticky white navbar + rich charcoal footer). Landing schedule table is DB-driven (`schedules` table, managed at `/dashboard/schedules`). Tools are DB-driven too (`tools` table, managed at `/dashboard/tools`) — the landing card grid, filter tabs, registration form picker, and validation all read from it; `config('bootcamp.tool_categories')` is only the migration seed.
- **Confirmations:** admin uses SweetAlert2 (CDN in `layouts/admin.blade.php`) — add `data-confirm="message"` to any form instead of `onsubmit confirm()`.
- **Exports:** every admin table gets its own "Export Excel" button (`.page-head` next to the title) backed by `maatwebsite/excel` and an export class in `app/Exports/`. No export links in the sidebar.
- **Admin sidebar:** grouped sections via `.side-heading` (Bootcamp / Academy / General), plain text nav items — no emoji/icons. Courses CRUD lives under Academy (`/dashboard/courses`).
- **Phone country codes** come from `giggsey/libphonenumber-for-php` via `App\Support\PhoneCountries` — don't hardcode country lists.
- **Transactional email:** delivered over the client's **cPanel SMTP** (`MAIL_MAILER=smtp`, `mail.<domain>`, port 465/`smtps`, username = full address — see `.env.example`). Every customisable email is declared in `config/email_templates.php` (default copy + placeholder list); admins override subject/heading/body/CTA at `/dashboard/email-templates`, stored in `email_templates` and merged by `EmailTemplate::resolve()`. Send through `App\Services\EmailNotificationService` (never `Mail::` directly for participant mail) — it renders `{{ token }}` placeholders, writes an `email_logs` row, and swallows/records failures so a mail outage can't break a request. `App\Mail\TemplatedMail` + `resources/views/emails/template.blade.php` are the shared wrapper. Bootcamp registration fires `sendRegistrationConfirmation()` alongside the SMS. Resends: per-row + bulk on the registrations table, the registration detail page, and `/dashboard/email-logs` (mirrors the SMS Delivery screen). The cPanel host must be the server hostname the TLS cert covers (`premium349-2.web-hosting.com`), **not** `mail.<domain>` — the shared-hosting cert is `*.web-hosting.com` and `mail.applydacademy.com` fails the handshake.
- **Bulk compose:** tick rows on `/dashboard/registrations` → bulk action "Send email to selected…" stashes the ids in the session (`BulkEmailController::SESSION_KEY`) and redirects to a compose screen (`Dashboard\BulkEmailController`). The message is rendered **once per recipient** so `{{ first_name }}` resolves individually, logged to `email_logs` with `template_key = bulk_broadcast`. Sends are synchronous — large selections block the request. **Registrants with `marketing_opt_in = false` are excluded by default and the exclusion is enforced server-side**, not just in the UI — the compose screen lists them in a separate "Excluded — opted out" panel and they get no `email_logs` row at all. The single override is a `service_message` checkbox, for mail consent doesn't govern (schedule change, joining link, cancellation); the skipped count is always reported back in the flash message so a drop never looks like a delivery failure. Transactional confirmation resends are unaffected — marketing consent doesn't gate them.
- **Filtering registrations by tool:** `RegistrationsTable::filters()` exposes a `MultiSelectFilter` whose options come from the `tools` table (never a hardcoded list). `registrations.tools` is a JSON array, so the callback OR-s `whereJsonContains()` per selected value — "anyone who picked any of these". That compiles to `json_contains()` on MySQL and `json_each()` equality on SQLite: exact element matching on both, never a substring. Note rappasoft validates multi-select values against the options list and silently discards unknown ones, so a tool deleted from `tools` stops being filterable (and tests must create the tools they filter on rather than leaning on the migration's seed list).
- **Deleting registrations:** per-row `Delete` button + `Delete selected` bulk action on `RegistrationsTable`, both gated on the existing `manage registrations` permission (checked server-side in `performDelete`/`performDeleteSelected` — Livewire methods are publicly callable, so the `@can` in the Blade partial is presentation only). Deletes are **permanent** — `Registration` has no `SoftDeletes`. Delivery history is preserved: `sms_logs.registration_id` is `ON DELETE CASCADE` at the DB level, so `detachLogs()` nulls it first to match `email_logs`' `nullOnDelete` — the person goes, the record of what we sent them stays. Confirmation uses the SweetAlert2 `confirm()` helper on the component (there is no form to hang `data-confirm` on in a Livewire action); `deleteRow`/`deleteSelected` only raise the dialog, the `perform*` methods do the work.
- **Rich text + images:** `resources/views/partials/quill.blade.php` is the shared Quill editor (`<textarea data-rich>`). Its image button uploads to `POST /editor/image` (`Dashboard\EditorImageController`, `auth` middleware, public disk under `editor/`) and embeds an **absolute** URL — never Quill's default base64, which mail clients strip. The button is hidden for guests. `App\Support\Html::clean()` allow-lists `img[src|alt|width|height]` and restricts URI schemes to http/https/mailto, so `data:` and `javascript:` sources are dropped. HTMLPurifier runs an HTML 4.01 doctype — HTML5 tags (`figure`, `figcaption`) throw, so don't add them to the allow-list.
- **Job board:** companies sign up at `/companies/register` (creates a user with the `company` role + a `Company` profile); company portal at `/company` (`layouts/company.blade.php`, role:company) for posting jobs and reviewing applications. Public board at `/jobs` (`JobOpening::open()` scope); applicants apply without an account, uploading CV + up to 5 supporting docs. **Application files are stored on the private `local` disk** (`storage/app/private/applications/...`), never the public disk — downloads only via authorized `company.applications.cv`/`.document` routes (owner-checked). Login redirects by role: company → `company.home`, others → `dashboard`.
- **Session videos:** recordings of past sessions, hosted on YouTube — the site never stores video files. CRUD at `/dashboard/videos` (`SessionVideoController` + `SessionVideosTable`, drag to reorder, Export Excel), public at `/videos` (`PageController::videos`, paginated) plus the newest three on the landing page (`#videos` section, hidden entirely when none are published). Admins paste **any** YouTube link — watch, `youtu.be`, embed, shorts, live — and `SessionVideo::parseYoutubeId()` normalises it to the 11-char id, which is what `session_videos.youtube_id` stores (unique, so the same video can't be added twice). The pasted `youtube_url` is a form field, not a column: parsing happens inside a closure rule so a bad or duplicate link is reported on the field the admin actually filled in. Thumbnails default to YouTube's own still (`i.ytimg.com/vi/{id}/hqdefault.jpg`); a custom upload (public disk, `videos/`) overrides it — the admin table needs `setAdditionalSelects(['session_videos.thumbnail'])` for that to render. Cards in `partials/video-grid.blade.php` are a **facade**: a plain link to the watch URL that script swaps for a `youtube-nocookie` iframe on click, so no YouTube request fires until someone presses play and the card still works without JS. `is_published` gates public visibility (`scopePublished`); ordering is `sort_order` on both sides. All the wording on `/videos` (hero, empty state, bottom CTA) and the landing strip's heading/lead/link is **CMS-editable** — registered under the `videos` page and the landing "Session videos strip" section in `config/cms.php`, read with `cms()`/`cms_html()`. Don't hardcode copy into either view.
- **Talent pool + recruiter credits:** candidates drop a CV at `/talent-pool` (public, no account) tagging up to 5 sectors from `JobOpening::SECTORS`; the file goes to the **private** `local` disk under `talent-pool/cv/`. A company sees a candidate only once it has published a job in a matching sector (`Company::matchingTalent()`), and the name is masked (`masked_name` → "Kwame A.") with **no contact details rendered at all** until it spends a credit — masked server-side, not blurred in CSS. Sector matching OR-s `whereJsonContains()` per sector (exact element match on MySQL and SQLite, never a substring), same shape as the registrations tool filter. **Credits are the only currency**: `creditsBought()` (sum of `plan_purchases` with `status = paid`) minus `creditsUsed()` (rows in `cv_unlocks`) — there is no balance column to drift, and no second way to earn credits. One credit opens one candidate permanently; the unique index on `(company_id, talent_profile_id)` makes a second click free, and the balance is re-checked inside `Company::unlockCv()`'s transaction. Credits never expire and buying again just adds another paid row — that is the whole "expand your plan" story, so there is no renewal, expiry or cron anywhere. **Applications to a company's own job posts stay free and never touch credits.** Plans are admin-CRUD at `/dashboard/recruiter-plans` (purchases snapshot `plan_name`/`credits`, so retiring a plan can't disturb what was bought); recruiters buy at `/company/plans` through the existing Paystack redirect, and `company.plans.callback` sits **outside** the auth group deliberately — verifying a payment must not depend on a live session. Offline payers get credits via the "Add credits by hand" form on `/dashboard/plan-purchases`, which writes a normal settled purchase row rather than inventing a second mechanism.
- **Pulse Check (session surveys):** short check-ins participants fill in around a session — public at `/check-in` (picker) and `/check-in/{slug}`, no login. **Surveys are rows, not config**: admins create as many as they like at `/dashboard/surveys/manage` (`SurveyManagerController` + `SurveysTable`), each with its own slug/URL, QR, questions and results. `config/surveys.php` is **only the migration seed** for both `surveys` and `survey_questions` — nothing in it is read at runtime. `surveys.slug` is the public route key (`Survey::getRouteKeyName()`), auto-generated from the name when left blank and refused for `Survey::RESERVED_SLUGS` (`thanks` would shadow `/check-in/thanks`). `is_active` closes a survey: off the picker, 404 on the form, **results still on the dashboard**. Data outlives the form — `SurveyManagerController::destroy` refuses while any response exists (archive instead), and deletes the survey's questions itself. Both `survey_id` FKs (`restrictOnDelete` on responses, `cascadeOnDelete` on questions) were added by a later `ALTER TABLE`, which **SQLite silently ignores** — so they hold on MySQL only and app-level enforcement is what the tests exercise. Never move that guard back into the database. **Duplicate** copies a survey plus its questions (never its responses) and lands closed — the way to re-run the same check-in for the next session while the previous one keeps its results. Three question types: `choice`, `scale` (answer is the 1-based index, `options` holds the labels), `text`. Answers land in `survey_responses.answers` as a JSON map keyed by the question `key` — which is why the key is set once at creation and **not editable afterwards** (changing it would orphan every answer already collected); deleting or hiding a question likewise leaves its answers in the table. Validation rules are built from the DB rows (`SurveyQuestion::rules()`), so the public form can never accept an option that isn't live. Skipped optional questions are omitted from the map rather than stored as `''`, so "answered" counts stay honest. The public form is a one-question-at-a-time stepper that **degrades to a single long form without JS** (`.pulse-form.is-stepped` is added by script). Results at `/dashboard/surveys`: a tab per survey (`?survey=<slug>`, falling back to the first), aggregates from `App\Support\Surveys::summarise()` counting in PHP (JSON map, bootcamp volumes), with a `SurveyResponsesTable` (`:survey-id`) underneath. The screen is deliberately **minimal until asked**: three stat numbers, then every block (share/QR panel, each question, the raw table) is a native `<details>` that starts closed — so it works without JS — and each question's summary row carries its headline figure (`summarise()` returns `top`, the winning bucket) so the closed state still says something. Cards there are **flat**: `.sv-flat` drops the 1px border and the hover lift, leaving spacing and a soft shadow. Don't put outlines back on them. That table's answer columns are rappasoft **label** columns, and rappasoft only SELECTs fields behind real columns — hence `setAdditionalSelects(['survey_responses.answers'])` in `configure()`, without which every cell silently renders as "not answered". Sharing: QR code on the results page plus a printable poster at `/dashboard/surveys/poster`, both drawn client-side from the route URL by **local** scripts — `public/js/qrcode.js` (qrcode-generator, MIT) plus the `public/js/qr-share.js` helper (`ApplydQr.draw`/`ApplydQr.copy`). They used to come off a CDN; don't put that back — one blocked request and the panel renders empty. Still no composer dependency, so the QR follows `APP_URL` — check it's right in production.
- **Questionnaires (general-purpose forms):** admin-built forms shared as a plain link — deliberately its **own** tables and screens, not an extension of Pulse Check (a check-in is a short fixed survey read in aggregate; a questionnaire is a form whose value is the individual submission). Admin CRUD at `/dashboard/questionnaires` (`Dashboard\QuestionnaireController` + `QuestionnairesTable`, drag to reorder), the field builder per form at `/dashboard/questionnaires/{slug}/build` (`QuestionnaireQuestionController` + `QuestionnaireQuestionsTable`, drag to reorder — that order is what the public page asks in), submissions at `/dashboard/questionnaires/{slug}/responses` (`QuestionnaireResponseController` + `QuestionnaireResponsesTable` + Export Excel). Public form at `/forms/{slug}`, no login, no picker page — the link *is* the distribution, and the build screen carries the copy button + QR (same client-side `qrious` CDN as Pulse Check, so it follows `APP_URL`). Ten field types in `QuestionnaireQuestion::TYPES` (`short_text`, `long_text`, `radio`, `checkbox`, `select`, `number`, `email`, `phone`, `date`, `file`); `OPTION_TYPES` are the ones fed by the options textarea, `settings` (JSON) holds the per-type extras (`max_select` for checkboxes, `mimes`/`max_kb` for uploads) so the row only carries what it uses. **Validation is built from the DB rows** (`QuestionnaireQuestion::validationRules()`, keyed by dotted path so the caller merges them into one `validate()`), so a form can never accept an option its admin never offered. Answers land in `questionnaire_responses.answers` as a JSON map keyed by the question `key` — which is why the key is set once at creation and **not editable afterwards**; a checkbox answer is a JSON array, and deleting or hiding a question leaves its answers in the table (the export therefore walks *all* questions, not just live ones). Skipped optional questions are omitted from the map rather than stored as `''`. **Uploads travel in their own `uploads[key]` input, never `answers[key]`**, so the validated answers bag never mixes plain values with `UploadedFile`s; files go to the **private** `local` disk under `questionnaires/{id}/`, get a `questionnaire_files` row, and are only ever served through the owner-checked `dashboard.questionnaires.file` route — the original filename is mirrored into `answers` so the table/detail/export all read one shape. Open/closed is one method, `Questionnaire::closedReason()`, used by the public page, the POST guard and the status badge alike so they can't disagree: unpublished = **404** (it's a draft), but published-and-outside-its-window / over its `response_limit` = a plain "this is closed" page, because that link was already handed out. The POST re-checks it — a window can lapse while someone has the form open. Deleting a form is refused while any response exists (unpublish instead); `questionnaire_responses.questionnaire_id` is `restrictOnDelete` and every FK is declared inside the `CREATE`, not by a later `ALTER`, so they hold on SQLite too. Deleting a response deletes its files off disk first. Duplicate copies the form plus its questions (never its responses) and lands unpublished. The public form is one plain long form — **no JS requirement at all**, no stepper; styles are the `.qform-*` block in `public/css/app.css`.
- **Conditional questions:** a questionnaire question can carry a `visible_when` rule — `{key, operator, values}` — naming an **earlier** question on the same form, with operators `in` / `not_in` / `answered` (`QuestionnaireQuestion::OPERATORS`). It points at the other question by `key`, the same handle answers are filed under, so a duplicated form carries its rules across intact. `App\Support\Questionnaires::visible()` is the **single** place that decides which questions are actually being asked: the public page, the validator and the store all read from it, so what's shown, what's required and what's kept can never drift apart. It walks in display order, and because a rule may only point backwards a chain resolves in one pass — if the controlling question is itself hidden, everything hanging off it is hidden too, whatever was posted. **The browser is never trusted:** every question renders into the page, script only hides the ones that don't apply (and `disabled`s their inputs, since a hidden `required` control blocks submission with an error nobody can see), and on submit the server recomputes visibility from the posted answers — so an answer smuggled in for a question that was never asked is dropped rather than stored, and a conditional question is only required once its rule is actually met. With JS off the whole form simply shows and the server sorts it out. `Questionnaires::controllersFor()` is what the admin picker offers: earlier, non-file questions only. The rule is validated server-side against the controlling question's live options, so a rule that could never be satisfied can't be saved. Admin UI is the folded-away "Only ask this sometimes" panel in the question modal (its value list is rewritten by script per chosen question, hence `data-no-select2` on those selects), and the questions table carries an "Asked when" column.
- **Seeded example form:** `DigitalSkillsQuestionnaireSeeder` (`php artisan db:seed --class=DigitalSkillsQuestionnaireSeeder`) loads the eleven-question digital-skills intake form, including the two conditional follow-ups (job title only for the employed; leadership detail only after "Yes"). It's `updateOrCreate`d on slug/key so re-running refreshes wording without duplicating rows or touching collected answers, and it lands **unpublished** so the copy can be read through before the link goes out. It is ordinary data, not config — edit or delete any of it from the dashboard.
- **Contact form From header:** the cPanel relay only accepts mail whose `From` is the mailbox it authenticated as and answers anything else with `550 … your domain <x> is not allowed in header From`. So `ContactController` leaves `from()` alone (Laravel stamps `MAIL_FROM_ADDRESS`) and puts the visitor on `replyTo()`. Same rule anywhere else participant-supplied addresses are involved — never set `from()` to someone else's address.
- **Finance (the books):** income and expenses at `/dashboard/finance`, with the invoice or receipt behind each entry attached. Gated on its own **`manage finance`** permission (seeded to `super` and `admin` by migration) *on top of* the `role:admin|super` group — it's the one dashboard area where "any admin" isn't automatically right, so take it off a role at `/dashboard/roles` if only some staff should see money. The sidebar group is `@can`-gated to match. **Income and expense share one table** (`finance_transactions.type`): every report worth having wants both sides together, and splitting them would mean writing every query twice. Amounts are **DECIMAL(12,2), never float** — this is the one place in the app where binary-fraction drift would be real money being wrong; `Finance::summarise()` totals in SQL (`SUM(CASE WHEN type = ?)`) rather than loading rows, since a ledger grows without limit. References carry the side in their prefix (`IN-…` / `EX-…`) and are re-issued if an entry is flipped over. Categories (`finance_categories`, admin-CRUD at `/dashboard/finance/categories`, drag to reorder) belong to **one side of the books** — the picker narrows by side in the browser *and* the server re-checks with `Rule::exists(...)->where('type', …)`, so a "Venue hire" income is impossible either way. A category in use can't be deleted or moved across the books (retire it instead); `finance_category_id` is `nullOnDelete` so history survives a deleted heading, and `recorded_by`/`uploaded_by` are `nullOnDelete` so removing a staff account never removes or blocks their entries. **Documents** (`finance_documents`, kinds `invoice`/`receipt`/`other`) go to the **private** `local` disk under `finance/{id}/` and are only ever served through the owner-checked `dashboard.finance.document` route — never the public disk. `App\Support\FinanceDocuments` is the single place files are written or removed: an entry has **one** invoice and **one** receipt, so re-uploading either replaces the old row *and* deletes the old file (re-uploading is how you fix a bad scan; a silent second copy nobody sees is worse than useless), while `other` documents accumulate. Deleting an entry deletes its files off disk first — the rows cascade, the files don't. **One period control:** the `from`/`to` form on the overview drives the stat cards, the category breakdown, the Livewire table (passed in as props, keyed on the period so it re-mounts) *and* the Export button, so the screen can never show four different windows; the table keeps only its Type and Category filters. The export splits money in and money out into **separate columns** rather than one signed figure — that's what a spreadsheet wants to total and how a cash book reads. Money in is `--success` green and money out is brand red (`.fin-in`/`.fin-out`): semantic per DESIGN.md rule 5, not decoration — the whole screen is scanned for which way the money went.
- **Student ID + portal login (after course registration):** completing a course registration issues the person a permanent **student ID** — an **8-digit code**: four-digit year of admission then a running number within that year, so 2026's first student is `20260001` (`App\Support\StudentIds`). Digits only, so it reads over the phone, types on a numeric keypad and prints on a card; the year in front keeps it sortable, says which intake someone came in with, and is what stops a new year's sequence from ever reaching last year's numbers. That caps a year at 9,999 admissions — widen the prefix, not the sequence, if that day ever comes. It also issues a real account on the shared `users` table, then sends both by **email and SMS**. Not to be confused with the existing Serial No + PIN: those are *application* credentials for this site's enrolment portal and stop mattering once the application is done. `App\Services\StudentAccountService` is the only place any of it happens. Registration finishes down two paths — a free course at the details step, a paid one at the tuition callback — and both already funnelled through one method, now `CourseEnrollmentController::completeRegistration()`, which is the single hook. **Issuing is idempotent**, because a callback can be replayed: a repeat call returns the same user and ID and a `null` password (the stored one is a hash and can't be read back). **The account belongs to the person, not the enrolment** — a second course matches on lower-cased email, keeps the same student ID, and *never* resets a password that already works. `users.must_change_password` marks an account still on the password we generated; it is what makes "resend login details" safe (it mints a new temporary password only when the student hasn't chosen their own, and says which happened in the flash message). **Students sign in to the sibling applyd-portal app, not here** — this site's `/login` leads to a `role:admin|super` group a student can't enter — so every link comes from `App\Support\Portal` off `PORTAL_URL`, and the new account is given the `student` role the portal's sign-in requires. Delivery is wrapped in try/catch at every level: a paid, completed registration must stand even if SMTP or the SMS gateway is down, and the admin can resend from the per-row action on `/dashboard/course-registrations`. The email is the `student_credentials` template in `config/email_templates.php`, which declares **its own `placeholders`** (the bootcamp tokens mean nothing to it) — the editor and the preview both honour a per-template list now, falling back to the shared one.
- **Shared database with applyd-portal:** `../applyd-portal` is a separate app on this same MySQL database, sharing `users`, `roles`, `courses` and `course_enrollments`. **applyd owns those schemas** — with one exception the portal declared: `course_enrollments.user_id`, which it added and backfills by email. Applyd's migration adds that column **only if it is missing** (same guard the portal uses), so whichever repo migrates second is a no-op and the live database never gets two. When adding a column to a shared table here, mirror it into the portal's `0000_00_00_000000_create_shared_tables.php` — that file is what stands the tables up for the portal's own test database, and it is a mirror, not a source.
- **Floating WhatsApp button:** on every public page via `partials/whatsapp-float` in `layouts/app.blade.php` — not the admin dashboard, not the company portal. The number, the greeting people start the chat with, and the tooltip are **CMS-editable** under the new `site` page (`/dashboard/cms` → "Site-wide"), which has no `route` key because it isn't a page. `App\Support\Whatsapp::normalise()` turns whatever an admin types (`0240835458`, `+233 24 083 5458`, `00233…`) into the digits-only international form wa.me needs, swapping a local leading `0` for `Whatsapp::DEFAULT_DIAL_CODE`. **Clearing the number in the CMS is the off switch** — which is why it reads through `Cms::stored()` rather than `cms()`: a saved blank must stay blank instead of falling back to the registry default the way every other field does. The green is WhatsApp's own mark supplied as `public/img/whatsapp.png`, so DESIGN.md's palette rule still holds for everything we draw (charcoal label pill, brand-red focus ring). It sits at `z-index: 55` — under the shared modal (200) and the landing promo bar (60).
- **Paystack charges passed to the payer:** `App\Support\PaystackFees` is the only place the charge is worked out, and the thing to understand is that **you cannot just add the fee to the bill** — Paystack takes its cut of whatever is *charged*, so `price + fee` still lands short. The bill is grossed up: `total = (net + fixed) / (1 - rate)`, rounded **up** to the pesewa (rounding down would leave the academy a fraction short on every transaction), then held at `cap` if one is set. Rates live in `config('services.paystack.fee')` / `PAYSTACK_*` env because they are Paystack's to change and vary by country and method — confirm against the dashboard, don't trust the defaults. `PAYSTACK_PASS_ON_FEE` is **off by default**: switching it on changes what every customer pays, which should be deliberate rather than something that arrives with a deploy. Applied at all three charge points (course form fee, tuition, recruiter plans). **The charge never touches the amount columns** — `amount`, `tuition_amount` and a purchase's `amount` all mean "what this is worth to the academy" and drive balances, revenue and the books; the charge goes in its own `amount_fee` / `tuition_fee` / `fee` column. On the way back, `base_amount` travels in the transaction metadata and the callback credits *that* against a balance (`CourseEnrollmentController::netPaid()`), with `PaystackFees::netFrom()` inverting the gross only as a fallback — otherwise a fully-paid tuition would read as overpaid by the fee. Customers see the breakdown before they commit (`partials/paystack-fee`), and the tuition screen's running total mirrors the same formula in JS — if you change one, change both; `tests/Feature/PaystackFeeTest.php` pins the PHP side and the two were checked against each other value-for-value.
- **Resending student logins:** `/dashboard/course-registrations` is where a student's portal login gets sent again — per row (the paper-plane action, `CourseEnrollmentController::resendCredentials`) or in bulk (`CourseEnrollmentsTable::sendCredentialsSelected`, SweetAlert2 confirm → `performSendCredentialsSelected`). Both go through `StudentAccountService::resendCredentials()`, so the same rules hold either way: **a resend can only ever be a new temporary password** (the stored one is a hash and can't be read back), and it is only minted for someone still on the one we issued — a student who has chosen their own keeps it and just gets the reminder. Registrations that aren't complete are **skipped, not sent**, and the skipped count is always reported back so a drop never looks like a delivery. The `Login details` filter (`sent` / `pending` / `ready`) is how you find everyone still waiting; the folded "Student logins" panel above the table carries the portal sign-in URL with a copy button, and **shouts if `PORTAL_URL` is unset** — links would otherwise point at this site, where a student can't sign in at all. `performSendCredentialsSelected` re-checks the role itself: Livewire methods are callable over HTTP by anyone who can reach them, so the admin-only route group is not the guard.
- **Portal URL:** the student dashboard (applyd-portal) is live at **`https://sts.applydacademy.com`**, and every student link is built from `App\Support\Portal` — the only place one is made. The address is a **constant on that class** (`Portal::DEFAULT_URL`) with `PORTAL_URL` as an override, not an env var with a fallback: the earlier shape fell back to `route('login')` whenever the setting was absent, which is exactly what a fresh deploy or a cached config looks like, and the links kept working and kept looking plausible while sending every student to a `role:admin|super` door. **`loginUrl()` can no longer return an applydacademy.com address at all.** `Portal::pointsAtThisSite()` catches the one remaining way to get it wrong — someone setting `PORTAL_URL` to the main site — and the "Student logins" panel on `/dashboard/course-registrations` shows the resolved link and flags that. Keep it in step with the portal's own `APP_URL`. If a change to `.env` doesn't show up, the server has a cached config: `php artisan config:clear`.
- **SMS to students must be one GSM-7 segment.** A single character outside the GSM-7 alphabet — an em dash, a curly quote — flips the whole message to UCS-2, where a segment is **70** characters instead of 160. `StudentAccountService::smsMessage()` was briefly three segments per student on the strength of one dash. Keep participant SMS to plain ASCII and under 160 characters; `StudentAccountTest` pins both.
- **Deleting from tables:** `App\Livewire\Concerns\WithRowDelete` is the one implementation — row delete, bulk delete, the SweetAlert2 confirm, and the permission check — used by every dashboard table (`RegistrationsTable` predates it and keeps its own). A table opts in and overrides only what differs: `deleteNoun()`, `deleteLabel()`, `deleteWarning()`, `deleteAbility()` (null falls back to the admin/super role), `deleteBlockedReason()` and `beforeDelete()`. Two of those carry the weight. **`deleteBlockedReason()` repeats the rule its controller already enforces** — "refuse a survey that has responses" is worthless if ticking the row and pressing Delete goes around it, so the guard exists on both paths (surveys/questionnaires with responses, a finance category in use, a course with registrations, an assigned or `super` role, your own account, the last super, a paid plan purchase whose credits are spent). **`beforeDelete()` is for what the database will not do** — files on disk (tool/course/post/video images, talent CVs, finance documents, questionnaire uploads) and rows that should be detached rather than cascaded. A refusal is never silent: `deleteSummary()` reports what was kept and why, so a half-successful batch can't read as a clean sweep. `performDelete`/`performDeleteSelected` call `abort_unless` themselves, because Livewire methods are reachable over HTTP by anyone who can reach the component. `CoursesTable` and `PostsTable` previously had bespoke bulk deletes with **no confirmation, no permission check and no guard** — those were replaced, not kept.
- **Impersonation ("view as"):** an admin can sign in as another account to see exactly what they see. `App\Support\Impersonation` is the whole feature: one session key (`impersonator_id`) holding whoever started it, while the logged-in user is the person being viewed. **It only ever goes downwards** — only a `super` may impersonate an `admin` or another `super`, because taking over a senior account would otherwise be a way to grant yourself the permission you were deliberately not given. Chaining is refused (it would make "who did this?" unanswerable and only get you halfway back), and **the impersonated account is never written to**, so an abandoned session leaves no trace on it. Start is admin-only (`POST /dashboard/users/{user}/impersonate`, the mask icon on `/dashboard/users`); **stop is open to any signed-in account** (`POST /impersonate/stop`) because the person pressing it is the impersonated user, who may hold no permissions at all. A charcoal banner is fixed to the bottom of every layout while it is active. Both start and stop are logged. The sibling **applyd-portal has its own copy** — deliberately, not shared: the two apps keep separate sessions, so an impersonation started here cannot carry across, and a student's dashboard only exists over there. Impersonate a student from the class roster in the portal; the portal's stop route sits outside the `password.change` gate so a student on a temporary password can still be exited. **Stopping also answers on GET (`impersonate.stop.get`), so the way out can be typed into the address bar** — the banner carries the button, but a banner only exists on a page that renders a layout, and an impersonated student hitting `/dashboard` lands on a 403 where it is nowhere on screen. GET changing state is deliberate here: the worst a forged request can do is hand an admin back their own account. That dead end is also why `resources/views/errors/` exists at all — `errors/minimal.blade.php` is a standalone shell (no layout, so it carries its own `<head>`) whose real job is the charcoal "Stop impersonating" panel; everything in it is wrapped in `rescue()` because the same view renders the 500 and the 503, where the session may not have started and a throw would replace the error page with a blank one.
- **Link previews (Open Graph):** what Facebook, WhatsApp, LinkedIn, X and Slack show when someone shares a page. `resources/views/partials/social-meta.blade.php` is the **single place** the tags are emitted — included from `layouts/app.blade.php` (public pages only; the admin and company portals are behind auth and never shared), and it also owns the `<meta name="description">` that used to be hardcoded bootcamp copy on every page. A page overrides any of it by defining a section — `og_title`, `og_description`, `og_image`, `og_type` — and pushing anything extra onto the `social-meta` stack (a post pushes `article:published_time`/`author`/`section`). Everything else falls back to the site card, so a page that defines nothing still shares correctly. A blog post shares its **cover image**, a course its image, a job its company logo; `public/img/og-default.jpg` (1200×630, cropped from `hero-bg.jpg`) is the fallback — swap the file, don't add a second default. **Never pass a value that can be null**: Blade reads `@section('og_image', null)` as the *opening* of a block section, so it calls `ob_start()` and waits for an `@endsection` that never comes — the buffer leaks and the section stays undefined. Coalesce to `''` (`$post->cover_image_url ?? ''`) and let the fallback work; `OpenGraphTest` asserts `ob_get_level()` is unchanged on the no-image paths precisely so that trap can't come back. Section content arrives **already escaped** (Blade `e()`s the two-argument `@section`), which is why the partial escapes its own fallbacks and prints every value with `{!! !!}` — `{{ }}` there double-escapes and ships literal `&amp;quot;`. `og:image` must be absolute, so it follows `APP_URL` — same caveat as the Pulse Check QR codes. Sharers **cache** what they scraped: after changing a post's cover, re-scrape at developers.facebook.com/tools/debug and linkedin.com/post-inspector or the old image keeps appearing.
- **Chasing payment (form fee + tuition):** `/dashboard/course-registrations` tracks **two separate payments** — the application form fee (`status`) and tuition (`tuition_status`) — so nothing on that screen says just "paid" any more: the filter is `Form fee`, the column is `Form fee`, and `Tuition` has its own filter with a `Form paid, tuition outstanding` option. Four stat cards count each side. `App\Services\PaymentReminderService` is the single place both reminder SMS are composed and sent; `CourseEnrollment::owesFormFee()` / `owesTuition()` are the single place "do they still owe this?" is decided, and every path (row button, bulk action, controller, service) asks them rather than re-deriving it. **Somebody who does not owe the money is skipped, never sent** — a reminder to someone who has already paid reads as "we lost your payment", which costs more to undo than the reminder was worth — and the skipped count is always reported back so a drop never looks like a delivery. Tuition is deliberately **not** chased while the form fee is unpaid: they get the form reminder instead, and two chasers at once is noise. Both messages are one **160-character GSM-7 segment** (`PaymentReminderTest` pins the length against a *longer* host than production's, so the headroom is real rather than a coincidence of today's `APP_URL`), which is also why the course title is left out and why `pay_token` is only 12 characters — every character spent on the link is one the message does not get. **The reminder link is the feature**: `GET /pay/{token}` (`enroll.pay`, public) re-opens Paystack for **that existing enrollment row**, so paying from a reminder settles the registration the student already started instead of creating a duplicate — before this there was no resume path at all, and `store()` minted a fresh row on every attempt. It is **one** route, not two, because a reminder is opened days after it is sent: what the link should do is decided when it is *followed* (form fee outstanding → checkout; form fee settled → sign them into `/application` for details or tuition). `pay_token` is deliberately not `reference`: re-opening checkout mints a **new** Paystack reference every time (Paystack ties a reference to one attempt and refuses a reuse), so the reference moves while the texted link has to keep resolving. The token is the credential, on the same footing as the Serial No and PIN — same phone, same SMS, same application. `form_reminder_sent_at` / `tuition_reminder_sent_at` are stamped **whether or not the gateway accepted it**: the question the `Reminded` column answers is "have we already chased this person?", and the delivery outcome lives on the SMS log. `pay_token` needs `setAdditionalSelects` alongside the other non-column fields the table reads.
